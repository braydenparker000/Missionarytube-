# Persistent shuffle and navigation

Independent base: release/astra-live-backport-20261009 at d7daef3d6aa43fdb9d6622843aa50d9de8a075d5. This branch does not include the Date Added change.

## Reproduced defect

On the unchanged release, start shuffle, advance twice, toggle off/on and advance again. A deterministic reverse-permutation fixture repeats a consumed song (3 unique selections out of 4) before exhausting six tracks. buildOrder rebuilt the permutation and moved the current track to its front, losing the consumed prefix.

## Behavior

The installed engine now keeps occurrence keys, persistent permutation ranks, a consumed set and a separate bounded navigation history/cursor. Each duplicate playlist occurrence remains eligible once per cycle. Previous/Next traverse history without spending new entries. Fresh choices consume the next unused rank. Intentional direct selections remain possible. Explicitly selecting a new category resets its cycle; toggles and checkpoint reloads retain it. Accepted source selections enter history, including selections whose later asynchronous media read fails; source preflight rejection never consumes a choice. This is selection history, not a claim that every entry was audibly completed.

Queue reconciliation retains surviving ranks/history/consumption and appends new occurrences. Explicit queues remain separate: they take priority and preserve the interrupted cycle on return, including exhaustion with repeat-off/all. Repeat-one does not draw a new entry. Repeat-all prepares a new cycle only after exhaustion and avoids an immediate boundary repeat when more than one occurrence exists. Existing ended-request guards and source retry budgets remain in place. Pending local crossfades use separate provisional requests; canceled candidates do not spend entries.

State uses the existing synchronous localStorage checkpoint plus IndexedDB, with bounded schema validation. Legacy checkpoints preserve their current selected occurrence, then start a new bag because old checkpoints did not record consumption. History is capped at 50,000 selections. There is no metadata/date fabrication, network call or media download in shuffle generation.

## Ordering research and tradeoffs

- [Fisher–Yates, NIST](https://xlinux.nist.gov/dads/HTML/fisherYatesShuffle.html): the permutation primitive preserves every occurrence.
- [Spotify, Fewer Repeats](https://engineering.atspotify.com/2025/11/shuffle-making-random-feel-more-human): generate candidates, score freshness, select a candidate.
- [Ruud van Asseldonk, merge-shuffle](https://ruuda.nl/2023/an-algorithm-for-shuffling-playlists): artist partitioning can optimize artist-run criteria; those guarantees do not apply to this implementation.

Song shuffle scores up to eight Fisher–Yates candidates for artist runs, known album adjacency and recent selections/plays. Unknown metadata is unpenalized, rather than treating unknown artists as one artist. Dominant artists are never dropped. Selection is a heuristic: nonuniform and not provably optimal. Album shuffle modes retain their grouped semantics. Work is capped at 16,000 candidate entries; catalogs over 8,000 tracks use one Fisher–Yates candidate to avoid unbounded scoring on the main thread. Existing ranks are not rescored during ordinary navigation.

Local 50,000-track model measurements were approximately 77ms generation and 88ms restoration (machine-dependent). This is bounded, but not evidence of a sub-frame budget on every phone; very large catalogs can still cause a one-time main-thread pause. Ordinary Next/Previous use a cached bag cursor instead of rescanning consumed prefixes. Exact-head browser/performance CI remains required before integration.

## Validation

Tests cover adversarial artist counts (2/4/4, 4/8/10, 99/1, homogeneous), duplicate and unknown metadata, multiset preservation, complete cycle coverage, history round-trips, reloads, toggles, queue additions/removal/refresh, manual queues, cycle boundaries, repeat modes, rejected source preflight, rapid canceled local fades and duplicate ended events. A seeded corpus compares candidate clustering against its first uniform permutation. Real Chromium runs exercise decoded audio, history, manual priority and checkpoint restoration.

No merge or deployment is performed by this task. The single release owner must integrate after exact-head qualification and review the documented large-catalog latency limit.
