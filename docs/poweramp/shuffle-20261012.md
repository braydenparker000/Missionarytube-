# Persistent shuffle and navigation

## Acceptance

- Failed reads and unplayed skips remain absent from successful-listening recency. Deliberate selections/skips stay consumed, and Previous/Next retain their selection-history cursor semantics.
- At 50,000 tracks, generation, restoration, queue reconciliation, album-mode changes and cycle generation run asynchronously. A mandatory Chromium test in the existing isolated, serial performance lane applies fourfold CPU throttling, requires event-loop progress, rejects tasks over 50ms during these operations, and verifies every occurrence survives.
- Preserve current occurrence, saved ranks, consumed set, history cursor, manual-queue priority, repeat modes, retry ownership, rapid canceled fades and duplicate-ended guards.

## Behavior

The engine persists occurrence ranks, a no-replacement consumed set and bounded navigation history. Duplicate playlist occurrences each remain eligible once per cycle. Previous/Next revisit selection history without spending another entry. Intentional direct selections remain possible. Starting a new category starts a new cycle; toggles and reloads preserve the existing cycle. Source preflight rejection consumes nothing; an accepted selection remains consumed even if its later media read fails.

Successful-listening recency is separate. Only the current element's accepted playback confirmation (or a verified real completion) enters recency. Failed loads and unplayed skips cannot supply freshness penalties. Manual-queue listening updates the interrupted base cycle's recency without consuming another base entry. Legacy selection-only checkpoints never migrate into listening recency.

Manual queues preserve the base cycle on return, including exhaustion with repeat-off/all. Repeat-one draws no new entry. Repeat-all generates a new cycle only after exhaustion and avoids an immediate boundary repeat when another occurrence exists. Pending local fades use provisional requests; canceled candidates do not spend entries.

## Large catalogs and persistence

Queues above 1,024 tracks use a same-origin worker. The worker is generated from the exact player model, with a test requiring byte-for-byte consistency. Metadata and results cross the worker boundary in bounded batches. Main-thread uploads, hydration and queue remapping yield between short slices; stale work cannot revive an old queue. Deliberate Next/Previous inputs wait for preparation, preserve their order, and are canceled by Pause or a new queue. Runtimes without workers use the same model in cooperative slices.

Checkpoints use compact queue indices and packed history/consumption. Cached JSON segments avoid rebuilding large identity/rank arrays in foreground writes; IndexedDB stores the already encoded large payload. Foreground writes can wait for preparation, while pagehide/freeze force the existing synchronous reload copy. Restore validates/remaps large queues in slices, retains duplicate occurrences and restores UI without downloading media or autoplaying.

No large metadata scoring or full state construction occurs on the main thread in the worker path. The mandatory browser test includes debounced persistence, rather than measuring only the permutation. It checks 50,000 occurrences, restoration equality and complete next-cycle coverage. Local worker measurements passed the 50ms task gate under fourfold CPU throttling; this is browser evidence, not a claim about every phone's display frame rate.

## Ordering research

- [Fisher–Yates, NIST](https://xlinux.nist.gov/dads/HTML/fisherYatesShuffle.html): every occurrence survives the permutation.
- [Spotify, Fewer Repeats](https://engineering.atspotify.com/2025/11/shuffle-making-random-feel-more-human): score candidate permutations for freshness.
- [Ruud van Asseldonk, merge-shuffle](https://ruuda.nl/2023/an-algorithm-for-shuffling-playlists): artist-run optimality is possible under its particular criteria; those guarantees do not apply here.

Song shuffle chooses among up to eight Fisher–Yates candidates, scoring artist runs, known album adjacency and confirmed listening/last-played recency. Unknown artists are unpenalized, and dominant artists are never dropped. This remains a nonuniform heuristic, not an optimality claim. The existing 16,000 candidate-entry cap and album grouping semantics are retained; ranks are not rescored during ordinary navigation.

## Reproduction and validation

The unchanged release repeats a consumed song after advancing twice and toggling shuffle off/on: a deterministic fixture produces three unique selections among four before exhausting six occurrences. The regression now passes.

Tests cover adversarial artist distributions, unknown tags, duplicate occurrences, multiset preservation, exhaustion, history round-trips, reload/toggles, queue edits, manual priority, errors, repeat modes, canceled fades, duplicate ended, failed-load recency, legacy migration, worker/model consistency and large-catalog browser responsiveness.

Integration and deployment remain with the release owner. The shuffle branch inherits the owner's live sorting release; its PR diff contains shuffle changes only. Qualification must pass on the exact final candidate before integration.
